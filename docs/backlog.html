1EExternalizar RxJS del bundle bugcondicional
core · sólo existe si 1D decide seguir publicando un bundle

El bundle actual embebe RxJS entero: cero imports externos en el ESM, cero require("rxjs") en el CJS. Por eso el ESM son 143 KB frente a los 67 KB del CJS.

Si se publicara, cualquier app que ya use RxJS acabaría con dos copias. Y este código es especialmente sensible: hace instanceof sobre tipos de RxJS y lee internals suyos (_finalizers, currentObservers). Con dos instancias eso falla en silencio. 

rollupOptions: { external: ['rxjs', /^rxjs\//] }

Hecho cuando: el bundle importa rxjs en vez de embeberlo. Muy probablemente esta issue no llegue a abrirse, porque 1D apunta a no publicar bundle.

3ALa app de ejemplo no tiene ruta 404 bug

{
  path: '/not-found',
  name: 'not-found',

La página 404 es la ruta marcada notFound: true. Con el flag en false la aplicación no tiene 404: una URL sin match no selecciona nada y deja en pantalla lo que hubiera antes. Es lo que copia todo el que empieza.

8Atest:types no arranca en Windows bug~2 líneas
scripts · sin dependencias, se puede hacer ya

scripts/check-public-types.mjs llama a npx y a npm.cmd con execFileSync sin shell: true. En Windows Node no puede lanzar un .cmd directamente, así que todas las llamadas mueren con spawnSync npm.cmd EINVAL.

La salida además engaña, porque el fallo de spawn se presenta como fallo de la comprobación: 

- types-contract does not compile:
      (vacío)
- @open-cells/core: could not pack (spawnSync npm.cmd EINVAL)
  ... una línea por paquete

Los dos son falsos. Comprobado a mano que lo que verifica sí pasa: npx tsc -p types-contract/tsconfig.json sale con 0 y npm run typchk -w @open-cells/core está limpio. Es decir, uno de los tres gates de CLAUDE.md —y parte de npm test— no se puede correr en local en Windows; en CI, que es Linux, pasa.

Ojo al arreglarlo: shell: true cambia cómo se citan los argumentos, y a tsc se le pasa la ruta del tsconfig como argumento. Hoy ninguna ruta del repositorio tiene espacios, pero el arreglo no debería depender de eso.

Hecho cuando: npm run test:types pasa en Windows y sigue pasando en Linux, y ningún fallo de spawn puede volver a disfrazarse de fallo de la comprobación.

8BLa cobertura de localize se hunde en un worktree anidado bugconfig
localize · 98,72 % fuera, 50,19 % dentro

La suite pasa —46 tests, 0 fallos— pero el total de cobertura cae al 50,19 % contra el 95 % del ratchet, así que el script sale con 1. El log se llena de esto: 

Error while generating code coverage for
  http://localhost:8000/__wds-outside-root__/2/node_modules/<pkg>/index.js
ENOENT: <worktree>\packages\localize\__wds-outside-root__\2\node_modules\<pkg>\index.js

web-test-runner sirve lo que queda fuera de su rootDir bajo el prefijo __wds-outside-root__/<N>/, y el paso de cobertura pega esa ruta detrás del directorio del paquete en vez de deshacer el prefijo. Los ficheros están en la raíz del worktree; la ruta simplemente no resuelve. El efecto colateral es que packages/localize/node_modules/sinon/pkg/sinon-esm.js acaba contando como fuente sin cubrir —se ve en las entradas SF: de coverage/lcov.info— y ese único fichero grande arrastra el total.

Es del entorno, no una regresión: main sin tocar, en un worktree bajo .claude/worktrees/, reproduce el 50,19 %; el mismo commit en un checkout normal da 98,72 % y pasa. Ocurre cuando el worktree cuelga de otro checkout que ya tiene su propio node_modules por encima.

packages/localize/web-test-runner.config.js no fija rootDir, así que toma por defecto el directorio del paquete. La vía a explorar es apuntarlo a la raíz del monorepo, para que las dependencias izadas queden dentro de lo servido y el escape __wds-outside-root__ no llegue a hacer falta.

Hecho cuando: la suite da el mismo porcentaje dentro y fuera de un worktree anidado, node_modules sigue fuera del informe, y el umbral del 95 % no se ha tocado — es un ratchet.
